## 2. 重点主题展开（关键步骤与断言序列）

### 2.1 生命周期/回滚/panic 隔离（CORE-028…031、038）

- `hardening.rs:53::failed_apply_rolls_back_effects_and_services`：setup `FailsAfterRegistering` 在 apply 中依次 `ctx.provide(TEXT,"stale")` → `ctx.effect(rollback 记录)` → `Err(PluginFailed("apply failed"))`。断言序列：①`ctx.plugin` 返回 `Ok`（创建成功≠激活成功）②`fiber.state()==Failed`、`fiber.error().is_some()` ③`root.get(TEXT) is None` ④`trace==["rolled-back"]`（effect 回滚且逆序）⑤健康 sibling 仍 Active ⑥后续 `inject=["hardening.text"]` 插件保持 Pending（死 provider 不得被注入）。
- `hardening.rs:89::panicking_apply_is_isolated_and_rolled_back`：同一插件 `panic=true`。断言：`ctx.plugin` **不 panic**、返回 Ok；Failed；`fiber.error()` 含 "panic"；service 无泄漏；trace 仍 `["rolled-back"]`。

- `hardening.rs:191::event_listener_panic_does_not_abort_dispatch`：第一个 listener panic，第二个写 "later"；`emit` 不 unwind，trace==`["later"]`。注意与 waterfall 相反：waterfall middleware panic 必须 fail-closed 重抛（redteam rt06/rt19）。
- `hardening.rs:409::failed_sync_activation_drains_async_cleanup_inline`：同步 apply 注册 async effect 后 Err。断言：plugin 返回 Ok；Failed；**函数返回时 trace 已含 "deferred"**（回滚内联 drain async lane，跨车道逆序）；再 `dispose_async()` 不重复。

### 2.2 异步取消 / dispose join（CORE-043/046）

1. **AsyncDisposer 取消恢复（S-1）** — `concurrency.rs:145::cancelling_dispose_async_restores_unstarted_effects`：fiber 上注册 sync effect("first") 与 async effect("second"，pending 永不完成)。`poll_once(dispose_async)` 返回 Pending 后 **drop future**。断言：①`fiber.state()==Disposed`（A-9：取消也必须完成 teardown）②trace==`["first"]`（未启动的 sync cleanup 被 inline 执行）③再次 `dispose_async` 幂等、trace 不变。`concurrency.rs:191`：直接 `AsyncDisposer`（first 立即完成、second pending）poll 一次后 drop → 重试 `dispose()` 后 trace==`["first"]`（未启动项恢复并执行一次）。`regression_semantics.rs:960`：`dispose_blocking` 是重试入口（restored_runs==1，之后 dispose no-op）；`:1012`：fiber 的同步 `dispose()` 会重试恢复的 async cleanup。
2. **fiber 卸载取消（A-9）** — `regression_core.rs:1754::a9_cancelled_dispose_async_completes_the_teardown`：注册顺序 older-async、newest-async、sync；drain 逆序先 sync（inline 计数 1）再 newest-async（挂起，poll Pending 时 drop）。断言：`state==Disposed`；`sync_ran==1`；`older_async_ran==0`（未启动→deferred，不丢不跑）；`registry.is_idle()`；latch 打开后 retry `dispose_async` → `older_async_ran==1`；registry keys 空。`regression_core.rs:1636::a2`：依赖关闭时 poll `refresh_async` 直到 Pending（consumer 处于 Unloading）→ drop；断言 consumer `Pending`、`registry.is_idle()==true`、重试 refresh 收敛（仍 Pending）；`regression_semantics.rs:1853::f4` 与 `regression_core.rs:3201::f4`：取消 recovery 不得 latch，下一次 `when_idle` 必须完成且无 `Unloading`（cleanup 不重复）。
3. **自 join（S-2 / R2-1）** — `regression_semantics.rs:1082`：cleanup 内对自己的 disposer 调 `dispose_blocking()`，必须立即返回（10s watchdog，线程完成）；`:1110`：cleanup 内 `await inner.dispose()`（同一个 disposer）必须立即返回（2s watchdog），外层 drain 结束后 `is_disposed()==true`；`:1144`：经由 `Fiber::dispose()` 的同一重入也不得死锁。关键区分：判定是 **drain frame（当前调用栈是否正在该 disposer 的清理帧内）而非线程 id**：`redteam4_attacks.rs:1142::r5_03` 断言同线程独立 joiner 必须等待（Poll::Pending），只有同一 disposer 的清理帧内自 wait 才短路。
4. **并发 join** — `semantics.rs:243`：两个 dispose 并发，总耗时 >=70ms、cleanup 恰好 1 次；`redteam3_attacks.rs:1904::at29`：multi-thread runtime 上第二个 dispose 来自独立线程必须等待（joiner 未 finished、runs==0），放行后 runs==1，完成后的第三次 dispose 立即返回（<300ms）。`redteam4_attacks.rs:1032::r5_01`：在第二个 await 点取消，已启动项计入 trace（如 `["s3","a2-start","s1"]`），未启动的 sync cleanup 逆序 inline 跑，状态 Disposed；重试不重复已丢的 in-flight 项。
5. **parked cascade recovery（F1）** — `regression_core.rs:3080`：8 深依赖链，poll root `dispose_async` 挂起后 drop → root `Disposed`，依赖者至少一个 `Unloading`；打开 gate 后 retry `dispose_async` → 所有依赖者 `Pending`，`registry.fiber_count()==fibers.len()-1`，每个 F0…F8 cleanup 恰好一次。`f1_dispose_all`（:3131）与 `f1_refresh_async`（:3159）是等价回收点（dispose_all 后全 Disposed/keys 空；refresh_async 后无 Unloading、idle）。`f4`（:3201）：第一次 when_idle 恢复中 drop，第二次必须完成（无 Unloading；4 个 cleanup 各一次）→ **recoverer latch 必须 RAII 语义**。`f5`（:3288）与 `f5_when_idle_sees_parked_frames_parked_after_entry`（:3579，分别测 Context 与 raw Registry）：入口有 active unload（跳过入口 recovery）→ 等待中 cancel 产生新 parked 帧 → 必须被 park/unload 完成事件唤醒、恢复全部帧、返回；断言依赖 cleanup 恰好一次、provider 的 deferred cleanup 在显式 retry 后恰好一次；`f5_repeated_cancel_then_when_idle_does_not_hang`（:3390）20 轮不 hang。
6. **取消边界总结（必须写进 Go 测试注释）**：cancel 时**已启动**的 cleanup future 丢失（A-9 唯一丢失项）；未启动的要么恢复（AsyncDisposer S-1）要么 deferred 到下次 dispose/drain（fiber A-9）；取消后 fiber 必须落在目标态（dispose→Disposed，refresh/restart卸载→Pending）；`AsyncDisposer` 层加锁/唤醒必须让 joiner 在 owner 取消后释放（`redteam3 at31/at32`：cancel 后 joiner <2s 返回、panic cleanup 只到 owner、joiner 不 hang）。

### 2.6 logger / clock / config / internal hooks / api surface（CORE-021/023/024/025/026/032/034）

- **internal hooks 顺序（CORE-021）**：加载插件时 trace 前 4 项固定 `["plugin:recorder","status:Pending","config:recorder:Loading","status:Loading"]`；即 plugin create hook → status(old=Pending) → config waterfall（此时 fiber 处于 Loading）→ status(old=Loading) → apply。dispose 时最近两条（从新到旧）是 `["status:Unloading","status:Active"]`，说明 status hook 的参数是**旧状态**，迁移是 `Active→Unloading`、`Unloading→Disposed`。config/update/get/set/listener/dispatch 的 veto/改写语义见 CORE-021 行；关键 Go 设计：hook 链每段必须能“不调 next”=veto，调 next 后仍可改写返回值；`internal/dispatch` 只在用户事件名上触发且不递归；raw bus 注册由调用者持有、不随 fiber 卸载。
- **logger（CORE-023）**：默认阈值 Info（Error=0…Debug=3 的数字序，spec:952-953）；buffer 是 ring（1000）、seq 单调；root 只安装服务不装 exporter；exporter 随 fiber 卸载；intercept 可改 name/level；非法数字 level 钳到 Error；`LogRecord::ts_unix_ms` 来自注入 Clock；`ctx.logger()` facade 在创建时快照 clock；`set_clock` 只能根 context（错误 message 含 "root"）。断言均见 CORE-023 行。
- **config（CORE-024）**：见 CORE-024 行；优先级 base→root intercept→child intercept→head；default 不覆盖显式值；validation 失败 `Validation` 且不替换旧 config；veto=Ok；hook 替换值需先校验才成为新 raw。
- **accessor/meta/isolate（CORE-025）**、**fiber 诊断（CORE-026）**、**trait-object 服务（CORE-032）**：见对应行。
- **api_surface 其他契约（CORE-023/025/034 补充）**：`LifecycleEvent::new` 快照+排序（CORE-044）；`on_lifecycle` 多订阅/panic 包含/drop 退订（CORE-044）；clock 单调性与 facade 快照（CORE-023）；`required_keys`（schema 元数据）、`insert_any`（meta）、`error_detail`（结构化错误）、`orphan_*` 计数（CORE-046 边界）。Go 侧这些对应 public API 的独立测试，不增加 CORE ID。

## 5. Rust 特有、无法直接等价翻译的用例与 Go 语义建议

### 5.1 CORE-033（无强引用环）与 CORE-051 的 Miri 泄漏检查

- Rust 依赖 `Arc`/`Weak` 引用计数和 drop 语义；测试用 `Arc::downgrade` 直接证明整图释放（`src/context.rs:2348`），CORE-051 用 `cargo miri test` 的 LeakSanitizer 级检查（`miri_leaks.rs:1-10`）。
- Go 没有引用计数、没有 Miri。等价测试建议：
  - 结构等价：在 fiber/context 上维护可选的 `Finalizer` 或显式 `Refs()` 诊断，测试 `root := NewRoot(); fiber := root.Fiber(); runtime.SetFinalizer(root, ...); drop references; runtime.GC(); runtime.Gosched()`，用 channel 等待 finalizer 触发，断言根图被回收（注意 finalizer 不保证及时，需多轮 GC + 超时；测试要 `t.Skip` 友好）。
  - 行为等价更重要：Go 用 goroutine 承载 async cleanup、用 timer/goroutine 承载 quiescence；CORE-051 的 Go 等价应断言“dispose_all 后无泄漏 goroutine、无挂起 timer、registry 空、二次调用 no-op”，并加 `runtime.NumGoroutine()` 基线对比（2000 轮 boot 循环后 goroutine 数不增长，对应 redteam9 t09 的 RSS 检查）。
  - 弱引用环问题在 Go 中由 GC 解决，不需要“防环”实现；但**不能**因此省掉“drop 后资源释放”的断言——泄漏点会变成 goroutine/timer/registry entry，而不是堆对象。
- 结论：CORE-033 在 Go 中标记为“语义已由 GC 保证”的**简化项**；CORE-051 保留全部可观察断言（清空/幂等/panic 优先/异步清理被 drain/无 goroutine 泄漏），Miri 部分替换为 `-race` + 泄漏基线检查。

### 5.2 CORE-034（BlockingExecutor）

- Rust 扩展：同步 dispose 要把 async cleanup 交给 embedder 安装的 `BlockingExecutor`（`executor.rs:38`，进程级一次性 `set_blocking_executor`；默认线程 park `block_on`）。
- Go 没有“同步 API 但需驱动 reactor”的矛盾：sync `Dispose()` 可以直接 `<-done` 等 goroutine/回调完成，不存在线程 park 驱动 reactor 的必要。因此：
  - 若 Go 保留 `BlockingExecutor` 兼容接口，测试语义 = `Dispose()` 必须通过该接口执行 async cleanup（可注入计数器断言恰好调用 1 次）；接口安装仅一次、返回 bool（进程级），测试需放独立 `_test` 包或 `TestMain` 串行。
  - 若 Go 不保留该接口：CORE-034 降级为“sync Dispose 必须同步等待 async cleanup 完成”，与 CORE-009/038 合并测试；在文档中明确“Rust-only 扩展，Go 无对应 API”。
- 建议：保留一个轻量可选接口（`WithBlockingExecutor`），便于 host 统一调度；测试文件独立（进程级状态），见 §4 的 `blocking_test.go`。

### 5.3 CORE-045/046/049 的 future 取消与“线程/goroutine 身份”问题

- **CORE-046（最重要）**：Rust 用“future drop = 取消”表达 dispose 取消。Go 没有隐式取消：
  - 建议 API：`DisposeAsync(ctx context.Context) error` / `Restore` 语义；`ctx.Done()` 触发时执行与 Rust 相同的 **A-9**：sync cleanup inline 跑完、未启动 async cleanup 放入 `deferred` 列表、状态落到目标态（Dispose→Disposed；refresh/restart 卸载→Pending），并唤醒 joiner；重试 `DisposeAsync/Dispose` drain deferred 恰好一次。
  - `AsyncDisposer` 等价：`type AsyncDisposer struct{ mu; queue; inflight; disposed }`，`Dispose(ctx)` 被 cancel 时把未启动项放回队列（S-1）；`DisposeBlocking()` 重试恢复项并 join in-flight。
  - **自 join（S-2/R2-1）**：Rust 用“drain frame（当前调用栈是否正在该 disposer 的清理帧内）”区分“self-join 立即返回”与“独立 joiner 必须等待”。Go 没有线程局部的调用栈标记，可选做法：给 cleanup 回调传入一个 `DrainFrame` token（`func(ctx context.Context, frame DrainFrame)`），disposer 记录“当前正在执行的 frame=g”；cleanup 内调用 `disposer.DisposeBlocking(ctx)` 时若 `ctx` 携带同一 frame（或 goroutine 正在该 disposer 的 cleanup 内，通过传入的 `frame` 参数显式可知），立即返回；独立 goroutine 没有该 token，必须等待。**不要**用 goroutine id hack 作为生产实现；测试可断言“自 join 立即返回（<监控阈值）/独立 joiner 等待”这一可观察契约。
  - 取消测试的等价断言：`ctx, cancel := context.WithCancel(...)` → 启动 `DisposeAsync(ctx)` → 在 cleanup 挂起（channel/sync gate）时 `cancel()` → 断言目标状态、deferred 列表、cleanup 计数、joiner 释放；再重试断言恰好一次。
- **CORE-045**：Rust 允许“同线程重入“（cleanup 内调自己 fiber 的 dispose）而拒绝“并发调用”。Go 无法可靠识别 goroutine；建议语义改为**操作 token + 继承**：lifecycle 操作创建 token 存入操作上下文；cleanup 通过 `Fiber.Context()` 能看到当前正在运行的 token（或 `DrainFrame`），因此“cleanup 内对自己的 fiber 发起 dispose/restart”被识别为 reentrant 而放行；其他调用一律 `ErrLifecycleBusy`。测试如实覆盖：(a) cleanup 内自 dispose 不阻塞；(b) 另一 goroutine 并发 dispose/restart/update → Busy；(c) async 操作挂起期间同 goroutine/其他 goroutine 的 sync 调用 → Busy（p2a 语义，Go 可实现：sync 调用不携带该 async 操作 token 即 Busy）；(d) 迁移（Go 无 worker 迁移问题，等价为“在另一个 goroutine 上恢复 polling”仍要 Ok —— 用 channel 把 future 状态转移模拟，或直接断言 token 在 goroutine 间不失效）。
  - 若 goid 方案被否：在文档中把“同线程”改写为“同一操作上下文/同一 drain frame”，并保留全部可观察错误/顺序断言。
- **CORE-049 的自身注册排除（C4）**：Rust 记录“创建注册的线程 id”，when_idle 减去调用者自己的注册。Go 建议用**帧对象替代线程身份**：`Plugin()` 在创建时把 `registrationFrame` 放进新 fiber 的 `Context`；`when_idle()` 若在 create hook 内经该 context 调用，则排除该 frame（`ctx.whenIdle()` 携带 frame 指针），外部 waiter 用 root context 无 frame → 完整等待。这样 C4（hook 内不等待自己）与 fix11b（外部 waiter 等待）都成立，且不需要 goroutine id。**注意**：排除范围仅 create hook；`Apply` 内同步等 when_idle 必须仍等待（Go 测试要显式覆盖“会阻塞/超时”的反面用例，或提供 `when_idle` 的超时 API 断言其未返回）。
- **CORE-046 的 parked recovery**：Go 中“cancelled cascade 留下 Unloading 帧”可用显式状态机复现；`WhenIdle`/`RefreshAsync`/`DisposeAll`/retried `DisposeAsync` 都必须先 recover；F4 用 RAII 等价（`defer releaseRecoveryLatch()`）；F5 等待循环在每次“unload 完成/park”事件后重新尝试 recovery，直到无 parked + 无 in-flight。

### 5.4 CORE-047 的 MAX_PLUGIN_DEPTH / 迭代卸载 / Weak ownership

- Rust 有 `MAX_PLUGIN_DEPTH=256`（按 fiber parent 链）；Go 应同样用显式计数器（`parent.Depth()+1`），不能依赖 goroutine 栈溢出：测试覆盖 254 层成功、第 256 层返回 `InvalidPlugin`；context-only 嵌套（extend/intercept/meta）不计深度。
- “深链迭代卸载”在 Go 中**不会**栈溢出（goroutine 栈动态增长），但契约要求顺序与 O(1) 栈；Go 测试应断言：1500 深链 dispose 的事件顺序 `L1500…L1,L0`、依赖者 Pending、不 panic；实现上用显式栈/队列（不要递归），可用 `runtime.Stack` 采样或代码审查保证；可选 10000 深链压力测试（顺序+耗时）。
- ownership 用 `Weak` 在 Go 中用**显式弱引用**模拟：父保存 child `*Fiber` 的 `weakRef`（如 `type weakFiber struct{ id uint64; get func() *Fiber }` 由 registry 查询，或在 Fiber 上加 `refs` 标记 + registry 弱表）；关键断言不是“弱引用类型”，而是：子自 dispose 后父 effects/child 列表不增长（churn 有界）、父 sweep 与子自 dispose 竞争收敛、取消的 child dispose 仍 detach。Go 没有 GC 弱指针 API（`runtime.AddCleanup` 可用于近似），建议 registry 作为唯一强引用表 + `Fiber` 句柄失效标志，测试断言同 Rust。

### 5.5 其他 Rust 专属细节

- **async plugin / Send future（CORE-035…037）**：Rust 的 `BoxFuture + Send` 是 executor 契约；Go 对应 goroutine/channel，无需断言 Send；断言等价为：`PluginAsync` 激活/卸载、sync API 对 async 插件返回 `ErrAsyncPluginNeedsAsync`、`refresh_async` 才能推进 async 依赖。
- **CORE-011/030 的 panic payload**：Rust `panic!` payload 可为任意 `Any`；Go `recover()` 得到 `any`。Go 测试应断言：drain 完所有 cleanup 后把**第一个** recover 值重新 `panic(v)`（或返回携带该值的错误），调用者能 recover 到同一个值；不要 `panic(fmt.Errorf(...))` 改写 payload。
- **CORE-038 的 inline drain**：Rust 经 BlockingExecutor；Go 直接同步等待，断言函数返回时 async cleanup 已完成（trace 已含 deferred）。
- **CORE-018 Bail 值语义**：Rust `Value::Null`/`Value::Bool(false)`；Go 用 `nil`/`false`（注意 `any(nil)` 与 typed nil 区分），断言 `Bail(nil)`、`Bail(false)` 不终止；`Bail("stop")` 返回该值。
- **CORE-020 next 可重复**：Rust `next.next()` 可多次调用并重跑剩余链；Go 的 continuation 必须是普通函数（非 once），terminal 被调用 2 次 → `[1,2]`。
- **CORE-024 JSON 数值**：Rust serde_json `json!(0.2)` 与 Go `json.Number`/`float64` 比较需统一（`reflect.DeepEqual` 在 `float64(0.2)` 与 `json.Number("0.2")` 上不等）；建议 Go 测试全部用 `json.RawMessage`/`any` 解码后 `cmp.Diff` 或自定义 canonicalize。
- **CORE-021 internal hooks 的类型化**：Rust 每种 hook 是不同函数类型（`ConfigNext`/`UpdateNext`/`GetNext`/`SetNext`/`ListenerOverride`/`DispatchInfo`）；Go 用接口/结构体承载，测试断言链式 next 的返回值传递、veto 的“不调 next”、listener override 的 prepend/global/once 继承。
- **CORE-023 tracing exporter**：Rust 用 `tracing` crate 适配器；Go 无对应全局 tracing 生态，可保留 `LogExporter` 接口测试，`TracingExporter` 标记 N/A 或映射到 `log/slog` handler 桥接。
- **CORE-012/021 的 `EffectMeta` 树**：Rust `EffectMeta{label, children}`；Go 用同构结构，测试必须精确比较树（含空 children `[]` 而非 nil 的差异——断言用自定义 Equal 或统一空切片）。
- **CORE-033 编号**：见页首对齐提醒，Go 测试文件命名建议直接写 `TestCore033RootGraphFinalizable` 之类以避免与 Rust 文件名混淆。
